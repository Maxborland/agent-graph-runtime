# Agent Graph Runtime v1.0 delivery specification

Status: implemented and technically verified on the current branch. The final
fresh-context review found no remaining P0-P2 blockers after remediation. This specification turns WP7-WP12 of
the accepted roadmap into observable behavior. A criterion is complete only
after its mapped tests and the final end-to-end acceptance pass on the delivered
revision.

## User and outcome

The user is a human operator who supplies a local Codex, Claude Code, Claudex,
or shell executor. They can run an adaptive graph across their own machines,
inspect and control it through a local UI, and recover or roll back repository
changes without granting workers or model providers coordinator authority.

## Scope

- Immutable plan revisions and validated graph patches activated between waves.
- Typed artifact production, consumption, hashes, and lineage.
- Resource-aware scheduling and bounded automatic decisions within a human
  mandate.
- A loopback-first local UI with authenticated commands and safe previews.
- A coordinator-owned SQLite WAL store, remote worker enrollment, leases,
  fencing, compare-and-set completion, and rejected-result evidence.
- Retention planning/pruning and integrity-checked portable exports.
- Authenticated TLS LAN access for user-controlled environments.

## Non-goals

- A hosted service, hosted UI, account system, telemetry backend, or provider
  credential storage.
- Giving workers approval, integration, persistence, or external-action
  authority.
- Automatically retrying uncertain external effects.
- Postgres support without measured multi-coordinator demand.
- Sandboxing an untrusted machine; enrolled workers remain user-controlled.

## Public interface

- Existing v0.6 and v0.7 graphs remain accepted. New optional run fields define
  budgets and automatic policy; node fields define resources, capabilities,
  produced/consumed artifacts, and estimated cost.
- `agr patch propose|list|activate` manages immutable graph patches. Safe
  patches may activate automatically only between waves and only within the
  current human mandate.
- `agr ui` starts an authenticated loopback server. `--lan`, `--cert`, and
  `--key` are required together for non-loopback TLS access.
- `agr worker serve|enroll|list` manages user-controlled workers. Dispatch is
  enabled only after the SQLite cutover marker is authoritative.
- `placement: "remote"` and `agr run --workers CONFIG` make remote dispatch a
  reachable CLI journey; the first run performs the locked cutover after it
  creates the initial projection.
- `agr storage migrate|status` performs and inspects the locked, backed-up,
  idempotent filesystem-to-SQLite cutover.
- `agr retention plan|prune` is dry-run first and preserves protected evidence.
- `agr export` writes an integrity manifest and portable run bundle.

## Acceptance criteria

- **AC1 — immutable adaptive plans:** every proposal records proposer, parent
  revision, patch hash, rationale, and timestamp. Activation creates a new
  immutable `PlanRevision`; the revision used by an active wave never changes.
- **AC2 — patch validation:** activation rejects cycles, missing dependencies,
  ownership conflicts, unsatisfied artifact contracts, unavailable capability,
  invalid resource claims, budget overflow, and authority expansion.
- **AC3 — crash-safe activation:** restart deterministically selects either the
  old or new active revision and never combines graph state from both.
- **AC4 — artifact lineage:** produced artifacts carry type, content hash,
  producer attempt, plan revision, and lineage. A consumer is blocked if bytes,
  type, or declared dependency drift before dispatch.
- **AC5 — resource scheduling:** named shared/exclusive resources, repository
  writing, worker capability, provider concurrency, and run concurrency are
  reserved atomically and released on every terminal attempt path.
- **AC6 — bounded execution:** node count, graph depth, duration, provider call,
  and optional cost budgets fail closed before dispatch. Accounting survives
  restart.
- **AC7 — safe automatic decisions:** deterministic policy may activate only
  reversible graph patches and pre-authorized actions inside the human mandate.
  Automatic patches cannot introduce trusted shell/check commands, replace an
  executor, or change external actions; every adaptive run is Git-isolated.
  Sensitive, unknown, or irreversible external effects still require an exact human receipt.
- **AC8 — protected local UI:** loopback UI uses an unguessable session
  capability, strict Host and Origin checks, CSRF tokens, no wildcard CORS,
  authenticated event streams, and command-specific preview/receipt validation.
  Negative browser/API requests cannot mutate state.
- **AC9 — SQLite cutover:** migration runs under the coordinator lock, hashes
  and backs up the source, imports idempotently into WAL tables, verifies all
  rows, and atomically writes one authoritative-store marker. Mixed or ambiguous
  state fails closed; rollback is allowed only before post-cutover mutation.
- **AC10 — least-authority workers:** enrollment grants capability-scoped,
  expiring credentials. Workers receive immutable attempt envelopes and can
  return only results, artifacts, and patch proposals; they cannot approve,
  persist coordinator state, integrate Git, or execute external actions.
- **AC11 — leases, fencing, and CAS:** SQLite allocates durable leases and a
  monotonically increasing fencing token. Only the current token can complete
  an attempt. Expiry uses coordinator receipt time, never a worker timestamp.
  Late, duplicate, malformed, or unauthorized results cannot alter
  accepted state and produce bounded append-only rejection evidence.
- **AC12 — coordinator verification:** accepted worker output is applied in a
  temporary clean worktree, rehashed, checked against ownership and artifact
  contracts, and verified before CAS. It reaches only the isolated run worktree
  after CAS and remains protected by a durable reconciliation intent.
- **AC13 — distributed recovery:** coordinator restart, worker loss, reconnect,
  reassignment, duplicate delivery, lease expiry, and stale completion preserve
  at-most-one accepted result and never duplicate an external effect.
- **AC14 — retention:** planning is read-only and reports exact protected and
  removable artifacts. Pruning requires explicit execution, retains minimal
  run/result/authority manifests, and never removes unresolved external-action
  or active-operation evidence.
- **AC15 — portable export:** export contains canonical state, revisions,
  attempts, leases, rejections, acceptance intents, evidence, results,
  operations, and a hash manifest. Export requires the run lock and uses one
  SQLite read snapshot. Verification
  detects missing, added, or changed bytes without trusting filenames.
- **AC16 — authenticated LAN mode:** non-loopback binding requires operator
  supplied TLS material and enrolled session credentials; plaintext LAN startup
  is rejected.
- **AC17 — compatibility and provider independence:** legacy local runs migrate
  deterministically, local-only execution remains available, and no provider
  API key or hosted dependency is introduced.
- **AC18 — consumption-surface acceptance:** from clean isolated coordinator and
  worker environments, a human can migrate, enroll, run, inspect, interrupt,
  recover, approve, integrate, roll back, export, and retention-plan using only
  documented CLI/UI information.
- **AC19 — release evidence:** build, full tests, distributed scenarios, package
  dry-run, Markdown links, staged-diff checks, and independent fresh-context
  review pass on the final revision.

## Risks and controls

- Duplicate external effects are controlled by coordinator-only dispatch and
  durable pre-dispatch approval consumption; workers never receive this task.
- Split-brain completion is controlled by SQLite transactions, lease expiry,
  fencing tokens, and compare-and-set acceptance.
- Adaptive scope expansion is controlled by immutable provenance, human mandate
  bounds, between-wave activation, and fail-closed validation.
- Browser-to-localhost attacks are controlled by session authentication,
  Host/Origin/CSRF validation, and command-specific confirmations.
- Migration ambiguity is controlled by source hashing, backup, a single marker,
  deterministic reconciliation, and crash injection at every seam.

## Traceable test plan

- AC1-AC4 → plan revision, graph patch, crash seam, and artifact lineage tests.
- AC5-AC7 → resource scheduler, persisted budget, and authority policy tests.
- AC8 and AC16 → loopback/LAN server tests plus negative Host, Origin, CSRF,
  CORS, session, WebSocket/event-stream, and plaintext-LAN cases.
- AC9 → representative legacy imports, idempotency, mixed-store, rollback, WAL,
  and cutover crash-injection fixtures.
- AC10-AC13 → two isolated worker environments covering enrollment,
  capabilities, lease loss, restart, duplicates, fencing, malicious payloads,
  ownership drift, and coordinator verification.
- AC14-AC15 → protected retention fixtures and export tamper verification.
- AC17 → the complete v0.6/v0.7 suite plus local-only executor fixtures.
- AC18 → CLI/UI distributed journey from a clean repository and databases.
- AC19 → `pnpm test`, package dry-run, link validation, `git diff --check`, and
  independent review after all fixes.
