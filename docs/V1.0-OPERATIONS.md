# Agent Graph Runtime v1.0 operations

This guide covers the self-hosted v1.0 control plane. The human supplies local
executor installations and credentials; AGR does not create provider accounts,
store provider API keys, or run a hosted service.

## Safe upgrade and SQLite cutover

1. Stop the run and verify that no coordinator or worker dispatch is active.
2. Back up the repository's `.agent-graph` directory using the operator's normal
   backup mechanism.
3. Run `agr storage migrate [RUN_ID] [GRAPH] --json`.
4. Inspect `agr storage status [GRAPH]` and confirm that
   `.agent-graph/AUTHORITATIVE_STORE.json` names the expected absolute database
   path and source manifest hash.
5. Enroll workers only after that marker is valid.

Migration acquires a repository-wide storage lock, verifies the hash-selected filesystem
generation and all accepted evidence bytes, writes a hash-addressed source
backup under `.agent-graph/migration-backups/`, imports a temporary SQLite WAL
database, and atomically publishes one store marker. Repeating the same command
is idempotent. A database without a marker, a marker without the matching import,
or a changed source manifest fails closed. A worker-only database created by
`worker enroll` can be adopted safely during the first `agr run --workers`;
run attempts or conflicting imports without a marker are never adopted.

Rollback to filesystem authority is intentionally not automatic. It is safe
only before any post-cutover mutation and requires removing the unpublished
temporary database plus restoring the untouched source backup under operator
control. After dispatch, recover SQLite and its WAL from backup; never point the
runtime at stale filesystem projections.

Node's built-in `node:sqlite` may print an experimental-feature warning on some
supported Node releases. The authoritative marker, source backup, and WAL must
be included in backup and upgrade checks.

## Worker enrollment and trust

```powershell
agr worker enroll --executors codex,claude --resources gpu --max-concurrency 1 --json
agr worker list --json
```

The enrollment response contains a one-time worker credential. Store it in the
user's existing secret store and configure the user-controlled worker endpoint.
Worker provider access comes only from that machine's local Codex, Claude Code,
or Claudex configuration.

Create a separate coordinator-to-worker bearer secret, store it in a file on
the worker, and start the worker against a clean clone:

```powershell
agr worker serve --worker-id WORKER_ID --workspace C:\worker\repo `
  --coordinator-token-file C:\secure\coordinator.token --executors codex,claude
```

Keep the coordinator configuration out of Git because it contains both scoped
credentials:

```json
{
  "databasePath": "coordinator.sqlite",
  "workers": [
    {
      "workerId": "WORKER_ID",
      "endpoint": "http://127.0.0.1:43123",
      "coordinatorToken": "same value as coordinator.token",
      "workerToken": "one-time token from worker enroll"
    }
  ]
}
```

Mark an `agent` or `review` node with `"placement": "remote"`, then run
`agr run .agent-graph\graph.json --workers .agent-graph\workers.json`.
For a first remote run, AGR creates the initial projection and performs the same
locked SQLite cutover automatically.

Workers receive immutable attempt and lease envelopes. They cannot access the
coordinator database, issue approvals, integrate or roll back Git, or execute an
`external_action`. The worker base clone is never reused as an attempt checkout:
the coordinator transfers missing clean Git objects and the worker creates a
detached per-attempt worktree. Transfers are capped at 40 MiB; larger snapshots
must first be distributed through the operator's normal Git path.

The coordinator rehashes patch bytes, checks fencing, ownership, and
deterministic checks in a temporary clean worktree. Only after coordinator-time
lease validation and CAS does it apply the patch to the isolated run worktree.
A durable acceptance intent supports restart reconciliation without replaying
work blindly. An enrolled worker is still a trusted source-code
environment; result verification is not a confidentiality sandbox.

## Adaptive graphs and automatic policy

```powershell
agr patch propose proposed.graph.json --rationale "add bounded verification"
agr patch list
agr patch activate PATCH_ID
```

Every proposal is immutable and records its parent, proposer, rationale, graph
hash, and reversibility. Activation is between waves only. Validation checks
schema, dependencies, cycles, typed artifacts, ownership, capabilities,
resources, budgets, and the existing human mandate.

`run.automaticPolicy.allowReversiblePatches` may activate a reversible pending
patch between waves. It cannot add/change an external action or trusted
shell/check command, or replace an existing executor. Every adaptive run is
Git-isolated before a proposed revision can execute. An action gate
is policy-approved only when the action is explicitly `reversible: true`, its
type appears in `run.automaticPolicy.allowedActionTypes`, and it remains inside
the human mandate. All other actions stop for `agr approve`.

## Local UI and LAN mode

`agr ui [GRAPH]` binds to `127.0.0.1` and prints a launch URL whose fragment
contains an unguessable session capability. Keep it private. Commands use a
short-lived, one-use preview plus session and CSRF validation. Host and Origin
must match exactly; wildcard CORS and unauthenticated event streams are absent.

Non-loopback access is opt-in and refuses plaintext:

```powershell
agr ui --lan --host 0.0.0.0 --public-host 192.168.1.20 --cert C:\secure\ui.crt --key C:\secure\ui.key
```

`--public-host` is the exact LAN hostname or address accepted by Host/Origin
checks; it is required for a wildcard bind. Use operator-controlled TLS material, firewall the port to intended machines,
and rotate the process session by restarting `agr ui`. The project has no hosted
UI or account recovery service.

## Retention and export

```powershell
agr retention plan --older-than-ms 2592000000 --json > retention-plan.json
agr retention prune --plan retention-plan.json --execute
agr export RUN_ID C:\archive\run-bundle
agr verify-export C:\archive\run-bundle --json
```

Retention is preview-first. Pruning requires the exact JSON plan the operator
reviewed; it never silently recomputes a replacement. The plan binds the exact run revision and generation
so a state change invalidates execution. Active runs, retry-blocked work,
unconsumed approval reservations, and unresolved external effects are protected.
Pruning keeps the authoritative generation and writes a permanent minimal
retention manifest. A custom SQLite authority outside the repository is listed
by its exact absolute path and is always protected.

An export is a portable directory containing canonical run artifacts and
SQLite attempt, lease, rejection, and acceptance-intent evidence plus
`EXPORT_MANIFEST.json`. Verification detects a changed manifest, missing or
changed bytes, and unmanifested additions. Copy the directory with a tool that
preserves exact bytes, then verify at the destination. Export acquires the run
lock and reads all SQLite material from one transaction snapshot; an active run
must first reach a quiescent state.

## Recovery decisions

- Expired or stale worker result: keep the bounded rejection evidence; never
  lower the fencing token or edit SQLite manually.
- Pending result acceptance after coordinator restart: reconcile the durable
  intent against the coordinator worktree, rerun checks, and complete CAS.
- Uncertain external action: inspect the effect, record reconciliation evidence,
  issue a fresh exact approval, then explicitly retry.
- Diverged target branch: use integration dry-run, resolve in the run branch or
  a clean checkout, and retry; never reset or force-push through AGR.
- Corrupt export: retain the source run and create a new bundle; do not repair a
  manifest to match unexplained bytes.
